MVP blueprint · v0

One engine: ad spend in, caused outcomes out.

The architecture has one job — take a release's marketing inputs and its outcomes from wherever they live, line them up in a unified model, and return how much of each outcome the marketing actually caused, per channel and per market, with intervals. Everything below serves that sentence.

The pipeline, end to end

Five stages. The first two are the hard, unglamorous part (getting consented data and joining it to a release); the middle is the moat (causal estimation); the last is what the client pays for (a number they can defend).

The methods layer, unpacked

Two products that share one engine, joined by a calibration loop. The MMM is always-on and retrospective; the experiments are planned and proactive; each makes the other more credible.

Always-on · retrospective

Hierarchical Bayesian MMM

Decomposes each outcome into baseline + per-channel incremental, pooling across releases so thin single-release data still identifies.

  • geometric adstock (carryover)
  • Hill saturation (diminishing returns)
  • NB likelihood for counts
  • partial pooling: release ⊂ client ⊂ genre
  • announcement-spike term
Planned · proactive

Geo-lift experiments

When a release tours many city-markets with staggered on-sales, that's a near-natural experiment — clean ground truth for what spend caused.

  • staggered difference-in-differences
  • synthetic control / CausalImpact
  • Meta GeoLift / TBR families
  • power analysis before spend
The bridge

Calibration loop

Experiment results become informative priors on MMM channel effects — so the always-on model inherits the rigour of the occasional gold-standard test.

  • experiment mROAS → MMM prior
  • shrinks unidentified channels
  • confidence rises per test run
  • the compounding-benchmark moat

The metric layer (what "Organize" sits on)

The dashboard's Organize → Dimensions / Metrics is the face of one layer that spans the warehouse and the methods. Its job: make sure every number resolves to exactly one definition, with its source composition or its model lineage shown — the same transparency promise the model makes.

Deterministic

Observed metrics

Arithmetic over already-clean warehouse facts. Computed in the transform layer (dbt). The composition is explicit — which source feeds each term.

  • streams, sales, spend, CTR
  • ROAS = Value⟨Beatport⟩ ÷ Spend⟨Meta+TikTok⟩
  • save rate, Shazam ratio
  • reads from: fact_outcome / fact_spend
Model-derived

Causal metrics

Not a formula — an estimate with a credible interval, produced by a model run. The thing a BI tool structurally cannot give you, and the reason this layer reaches into stage 4.

  • incremental, baseline, mROAS
  • announcement lift, confidence
  • reads from: model_estimate + run
  • can wrap an observed metric as its outcome
The boundary

Harmonize ≠ compose

Two steps people conflate. Field harmonization — mapping each platform's messy cost / spend / value naming into one unified field — happens at ingestion (stage 2). Metric composition happens here, over fields that are already clean.

  • harmonize: stage 2, per connector
  • compose: this layer, per metric
  • so the bank never touches raw naming

One consequence worth stating: observed and causal metrics feed the same bank from two different stores — observed from the fact tables, causal from model_estimate. The dashboard doesn't care which; it asks the metric layer for "incremental Beatport ROAS" and the layer knows whether to compute it or fetch it. That indirection is what lets the services-first BI build and the eventual custom app share one definition of every number.

Recommended stack (MVP-pragmatic)

Bias toward boring, hosted, and fast-to-first-result. The services-first model means you can lean on a BI layer over the warehouse before building a bespoke frontend — buy time, prove value, then build.

Where to draw the v0 line

The temptation is to build the platform. The MVP is a sharp retrospective read on one client's recent releases — enough to earn the pilot and the next conversation.

In v0

  • One client, electronic beachhead (Beatport + FUGA + Meta/TikTok)
  • Manual/CSV ingestion is acceptable — entity resolution done semi-by-hand
  • Retrospective MMM on past releases + announcement decomposition
  • One per-release scorecard + one portfolio roll-up
  • The semantic layer (every metric defined once)
  • An exportable defend-the-spend report

Deliberately not yet

  • Self-serve connector onboarding (do it for them)
  • Real-time / always-on refresh (weekly batch is fine)
  • Automated geo-lift design (run one by hand first)
  • Cross-client benchmark library (needs N clients — the moat comes later)
  • Multi-tenant auth, billing, the full app shell
  • Owned-content capture (the hardest X; approximate or annotate)
